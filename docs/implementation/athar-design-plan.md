# خطة تنفيذ وتصميم موقع أثَر

## الهدف
توحيد تجربة صفحات أثَر والتحقق من عملها على الجوال واللوحي والحاسوب، مع الحفاظ على الهوية البصرية المعتمدة وعدم استبدال الشعار أو الخطوط أو الألوان بصياغة تصميمية جديدة.

## القيود المعتمدة
- اعتماد `design-system/athar/MASTER.md` مرجعًا بصريًا؛ الألوان الفاتحة والوردي الهادئ والأخضر المريمي والذهبي والنص الداكن.
- العربية واتجاه RTL في صفحات الموقع العربية.
- عدم تغيير ملفات الشعار أو الرسوم أو الخطوط المعتمدة ضمن هذه المرحلة.
- إعطاء الأولوية للكود، ولوحة المالك، وصانع الأسئلة، ثم إصلاح العيوب المكتشفة.
- عدم الادعاء بأن تسجيل الدخول أو قاعدة البيانات أو رفع الملفات يعمل فعليًا دون اختبار الخدمة الحقيقية.

## نطاق الصفحات
1. الرئيسية `index.html`: وضوح الإجراء الأساسي، روابط الدورات والتدريب، خطة المذاكرة، الأسئلة الشائعة والإشعارات.
2. الدورات `courses.html`: عرض مساري «تأسيس من حديد» و«الخطوة الأخيرة» بوضوح، وعدم الإيحاء بوجود محتوى غير مرفوع.
3. التدريب والاختبار `practice.html` و`exam.html`: وضوح السؤال والاختيارات والتغذية الراجعة والنتيجة.
4. صانع الأسئلة `mcq-builder.html`: صلاحيات المالك/المشرف، إنشاء الأسئلة واستيرادها وتصديرها، التحقق من PDF، وعدم تسريب صلاحيات الإدارة للطالب.
5. لوحة المالك `admin.html`: إدارة المحتوى والروابط والملفات، التحقق من النوع والحجم، وحالات النجاح والفشل.
6. تسجيل الدخول `auth.html`: التحقق من إعدادات مزود OAuth وعناوين إعادة التوجيه في Supabase؛ هذه الإعدادات الخارجية لا يمكن إثباتها من فحص الملفات وحده.
7. المصادر وخطة المذاكرة وبقية الصفحات: سلامة الروابط، وضوح المحتوى المتاح، واتساق RTL.
8. صفحة الخطأ `404.html`: رسالة واضحة ورابط رجوع إلى الرئيسية.

## مراحل التنفيذ
### المرحلة 1 — خط أساس وفحص
- تشغيل `python3 scripts/check_site.py` و`python3 scripts/validate_static_site.py`.
- تشغيل `python3 scripts/test_quiz_content.py` و`python3 scripts/test_llm_integration.py`.
- فحص الروابط المحلية، وعناوين الصفحات، وخصائص العربية وRTL، والموارد المحلية.

### المرحلة 2 — الوظائف ذات الأولوية
- مراجعة حراسة الوصول إلى صانع الأسئلة ولوحة المالك في الواجهة والخدمات الخلفية وسياسات Supabase RLS.
- اختبار إنشاء السؤال وتعديله وحذفه والاستيراد والتصدير، والتحقق من رفض JSON غير الصحيح.
- مراجعة رفع الملفات والروابط الخارجية والتحقق من MIME والحجم وبروتوكول HTTPS.
- إعادة اختبار تسجيل الدخول بعد تأكيد إعدادات Google OAuth وSupabase من لوحة الخدمة.

### المرحلة 3 — التوافق وإمكانية الوصول
- فحص العروض 375 و768 و1024 و1440 بكسل.
- التحقق من ظهور التركيز بلوحة المفاتيح، وتسميات النماذج، وأسماء الأزرار، والتباين، واحترام `prefers-reduced-motion`.
- تجربة الروابط والتنقل وحالات الخطأ والنجاح في المتصفح، وتسجيل أي اختبار يتعذر تنفيذه بسبب غياب حساب أو بيانات خدمة.

### المرحلة 4 — البناء والنشر
- إعادة بناء النسخة الثابتة عبر `python3 scripts/build_static.py`.
- إعادة تشغيل جميع الفحوص بعد البناء.
- مراجعة `git diff` وعدم إدراج مفاتيح أو بيانات سرية.
- النشر خطوة مستقلة؛ نجاح الاختبارات لا يعني أن النسخة المنشورة تم تحديثها.

## معايير القبول
- لا توجد روابط محلية مكسورة أو أخطاء HTML أساسية في الفحوص الآلية.
- جميع الصفحات العربية الأساسية تستخدم `lang="ar"` و`dir="rtl"`.
- لا يمكن للطالب الوصول إلى أدوات الإدارة بمجرد تعديل الواجهة؛ يجب أن تمنع سياسات الخادم ذلك أيضًا.
- لا توجد ادعاءات غير مختبرة عن تسجيل الدخول أو التخزين السحابي أو مزايا الذكاء الاصطناعي.
- يُذكر في تقرير كل جولة ما نجح آليًا، وما اختُبر يدويًا، وما بقي معطلًا أو غير قابل للتحقق.

- أُضيفت حالة فارغة مفيدة في `resources.html` مع روابط للدورات والتدريب، وأُضيف دعم تصنيفات كمي ولفظي وعام في صانع الأسئلة.

- نجحت فحوص البناء والروابط وRTL والمحتوى وتكامل LLM وفحوص JavaScript. يجب إعادة تشغيلها بعد دمج آخر تغييرات الأمان.
- بقي تحذير Supabase واحد: حماية كلمات المرور المسرّبة معطّلة وتحتاج تفعيلًا من إعدادات Auth. إعداد Google OAuth وعنوان إعادة التوجيه الخارجي يحتاجان تأكيدًا من Google Cloud وSupabase Auth.
- لا توجد مواد منشورة في `course_content` حاليًا؛ تعرض صفحة المصادر حالة فارغة واضحة بدل الادعاء بوجود ملفات غير مرفوعة.
- المعاينة كانت تعمل خلال الاختبار السابق، لكن فحص حالة بيئة التطوير في هذه الجولة وجد الخادم غير مستجيب؛ أُعيد تشغيله وأصبح يرد HTTP 200 على المسارات الأساسية.

## المتبقي قبل اعتماد الإصدار
- إعادة تشغيل الفحوص الأمنية واختبار سياسات RLS بعد آخر migrations.
- مراجعة تغييرات المساعد وتوليد الأسئلة وحدود الاستخدام، ثم اختبار المسارات في المعاينة بعد استعادة الخادم.
- مزامنة التغييرات مع أحدث `origin/main` قبل دفعها أو النشر؛ المستودع المحلي كان متأخرًا عن الأصل.
- اختبار لوحة المالك ورفع الملفات ونشرها وإلغاء نشرها وحذفها بحساب مخوّل، وتأكيد OAuth، ثم نشر منفصل والتحقق من الإنتاج.

## جولة التحقق الإضافية — 2026-10-21
- اكتُشف عطل فعلي في واجهة `mcq_public_questions`: العرض الآمن باستخدام `security_invoker` كان يُرجع HTTP 401 بسبب عدم امتلاك دور `anon` صلاحيات أعمدة الجدول الأساسي. أُصلح بمنح أعمدة السؤال والاختيارات والتصنيف والصعوبة والتواريخ فقط، وإزالة شرط `status` من تعريف العرض والاعتماد على RLS لتصفية الأسئلة المعتمدة.
- بعد الإصلاح: طلب REST إلى `mcq_public_questions` أعاد HTTP 200 وصفوفًا صالحة. فحص الصلاحيات أكد أن `anon` لا يستطيع قراءة `correct_index` أو `explanation` مباشرة، بينما يظل العرض الآمن قابلًا للقراءة.
- أُعيد اختبار الاختبار المؤقت في Chromium: حمّل 10 أسئلة، ولم تظهر الإجابات الصحيحة قبل التسليم، ثم صحح الخادم الإجابات وأظهر مراجعة الأسئلة العشرة بلا أخطاء JavaScript مرصودة. أزيلت محاولات الاختبار المؤقتة من قاعدة البيانات.
- اختبارات الأمان والمساعد وتوليد الأسئلة والبناء والروابط وRTL نجحت بعد التعديلات.
- فُحص مساعد أثَر الإنتاجي: حد الاستخدام الدائم يعمل، لكن مزوّد OpenRouter أعاد 401 بسبب بيانات مصادقة غير مقبولة. حُدّثت Edge Function لتطبيع المفتاح وإظهار رسالة إعداد واضحة بدل خطأ 502 عام، ونُشرت النسخة 9. أعاد الاختبار الآن HTTP 503 برسالة صريحة تفيد بأن المفتاح أو عنوان المزوّد يحتاجان تصحيحًا؛ لا يمكن إتمام اختبار رد ذكاء اصطناعي ناجح حتى يُضبط سر `LLM_API_KEY` الصحيح و`LLM_BASE_URL` المطابق.
- الموقع العام على Render يعيد HTTP 200 للمسارات الأساسية، لكنه لم يكن يعرض بعض تغييرات المعاينة في لحظة الفحص؛ يلزم دفع آخر التعديلات ثم التحقق من إعادة نشر Render قبل إعلان الإصدار العام مكتملًا.
