# حزمة تطوير نبراس — جاهزة للاستخدام مع وكيل البرمجة

هذه الحزمة مرجع عملي يمكن نسخه إلى Codex أو أي وكيل برمجي متصل بمستودع نبراس. المهارات الموجودة داخل `.agents/skills/` هي تعليمات محلية للوكيل، وليست ميزات ذكاء اصطناعي تظهر للطلاب بحد ذاتها.

## 1) المهارات المحلية المتاحة

- `nibras-frontend`: بناء الواجهات مع نظام التصميم.
- `nibras-qa`: فحص الصفحات والسلوك.
- `nibras-security`: مراجعة الأمان والصلاحيات.
- `nibras-ai-tutor`: مواصفات المدرس الذكي العربي.
- `nibras-learning-design`: تصميم رحلة التعلم والتدريب والخطة.
- `nibras-backend-data`: قاعدة البيانات والمصادقة والرفع.
- `nibras-accessibility`: إمكانية الوصول وRTL والتجاوب.
- `nibras-content-quality`: مراجعة الأسئلة والمحتوى العربي والرياضي.
- `nibras-release-ops`: الاختبارات والإطلاق والتحقق بعد النشر.

## 2) نص جاهز للنسخ إلى Codex

انسخ النص التالي كما هو بعد فتح مستودع `omar2007-ib/Nbras-` في أداة البرمجة:

> اعمل على مستودع نبراس الحالي، ولا تبدأ مشروعًا جديدًا أو تستبدل الملفات الموجودة بلا داعٍ. اقرأ `README.md` و`AGENTS.md` و`design-system/nibras/MASTER.md` وكل المهارات داخل `.agents/skills/` أولًا. افحص بنية المشروع والصفحات الحالية قبل التعديل.
>
> الهدف: تطوير منصة عربية RTL للاستعداد للقدرات الكمي، متجاوبة مع iPad والجوال والحاسوب، مع الحفاظ على الدورتين «تأسيس — تأسيس من حديد» و«تدريبات — الخطوة الأخيرة» وهوية التصميم الحالية.
>
> نفّذ العمل على مراحل صغيرة قابلة للمراجعة: (1) فحص الوضع الحالي والروابط والأخطاء، (2) إصلاح الواجهة وإمكانية الوصول، (3) تحسين إنشاء الأسئلة والتدريب وشرح الإجابات، (4) تصميم قاعدة البيانات والصلاحيات بأمان، (5) تجهيز رفع الملفات والمحتوى، (6) إضافة المدرس الذكي فقط بعد اختيار مزود وربطه فعليًا من جهة الخادم، (7) اختبارات شاملة وتوثيق النشر.
>
> استخدم المهارة المناسبة لكل مرحلة. لا تنسخ كودًا خارجيًا تلقائيًا؛ راجع الترخيص والاعتماديات والأمان قبل أي اقتباس. لا تضع أسرارًا في Git. لا تدّعِ أن المصادقة أو قاعدة البيانات أو رفع الملفات أو الذكاء الاصطناعي يعمل قبل اختباره end-to-end. إذا احتاجت خطوة إلى مفاتيح أو إعداد يدوي من لوحة خدمة، أوقف هذه الخطوة واشرح الإعداد المطلوب بدل اختلاق قيم.
>
> بعد كل مرحلة: شغّل `python scripts/check_site.py`، واختبر التغييرات، واكتب الملفات التي تغيّرت ونتائج الاختبار وما بقي. لا تحذف وظائف موجودة ولا تغيّر الهوية أو أسماء الدورات دون سبب واضح. ابدأ الآن بالتدقيق وإصلاح المشكلات المثبتة، ثم اعرض خطة قصيرة قبل أي تغيير معماري كبير.

## 3) ترتيب التنفيذ المقترح

1. **أولًا — سلامة الموقع:** إصلاح الروابط، أخطاء HTML/JavaScript، والتجاوب.
2. **ثانيًا — التدريب:** التأكد من حساب الدرجات، شرح الحلول، واستيراد/تصدير الأسئلة.
3. **ثالثًا — المحتوى:** نموذج بيانات واضح للدورات والدروس والأسئلة، مع تمييز المحتوى المنشور عن المسودات.
4. **رابعًا — الخلفية:** تفعيل Supabase وإعداد المصادقة وRLS والتخزين الخاص بعد التحقق من حالة المشروع.
5. **خامسًا — الذكاء الاصطناعي:** مقارنة مزودي النماذج من حيث دعم العربية، الخصوصية، حدود الاستخدام، والتكلفة؛ المفتاح في الخادم فقط.
6. **سادسًا — الجودة والإطلاق:** اختبارات آلية، تجربة iPad والجوال، فحص الصلاحيات، ومراجعة إعدادات النشر.

## 4) حدود يجب معرفتها

- إضافة ملف مهارة إلى GitHub لا تثبّت المهارة تلقائيًا في كل تطبيق؛ يجب أن تدعم أداة البرمجة مجلد `.agents/skills/` أو أن تُقرأ تعليماتها صراحةً.
- وجود ملفات إعداد Supabase لا يعني أن المشروع متصل أو أن تسجيل الدخول يعمل.
- تخزين `localStorage` محلي في المتصفح وليس مزامنة بين الأجهزة.
- وجود رابط لمزود نموذج مجاني لا يضمن توفرًا دائمًا أو استخدامًا بلا حدود.
- لا ترفع بيانات طلاب حقيقية أثناء التجربة، ولا تضع أسرار الخدمة في المستودع.
